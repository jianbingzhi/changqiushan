## 一、技术总方案（综合后端+前端分析）

### 1. 基石：B26 时段生成重构（派生 + 首单惰性物化）
- **派生层**（新增 `src/modules/booking/domain/slot-derive.ts`，纯函数）：`deriveSlots(dateStr, enabledTemplates, holidayOverride) → DerivedSlot[]`。闭园特例→[]；否则 `inferDayType`(复用) 选模板，各渠道名额来自模板。虚拟 id = **确定性 UUIDv5(date+startTime)**，使虚拟 id 与物化后 id 一致（下单免一次回查、并发更稳）。
- **读路径**：service 新增 `listSlotsForDate(date)` = 合并「已物化 `booking_slot` 行（带真实 booked/checkedIn）」+「派生虚拟行」，按 startTime，**已物化优先**。取代裸 `listSlotsByDate`（repo 仍保留供合并）。
- **写路径**：`createBookingOptimistic` 改为事务内 **`INSERT … ON CONFLICT(date,start_time) DO NOTHING`（首单惰性物化）→ `SELECT … FOR UPDATE` 取真实行 → 原子配额 UPDATE 守卫**。capacity/各渠道名额**只信服务端派生、绝不信前端**。
- **废弃 cron 预生成**：`rollGenerateSlots` + cron route 降级为可选预热或删；`copyDaySlots` 重定位为"提前固化派生行"运营动作。
- **无 DDL**（纯应用层重构，风险远低于建表）；存量已物化行靠"已物化优先"合并兼容；首单 INSERT 触发现有 `slot_changed` SSE（前端能收到行出现，是好事）。
- **对前端的契约产物**：派生能力同时导出 `quotaRuleService.resolveMonth(year, month) → DayCell[]`（每格 date/dayType/source(BASE|OVERRIDE|CLOSED)/totalQuota/usedQuota/materialized）——**B31 日历直接消费**。

### 2. 随 B26 同批：R-承载口径统一 + B31 规则层
> 后端强约束：**B26 + R-承载 + B31 规则层是同一段下单/容量核心代码，合并一个开发批次、一次并发测试，不分三次改 `createBookingOptimistic`。**
- **R-承载**：熔断分母统一用瞬时承载量（`configService.getInstantCapacity()` / `shared/lib/capacity.ts resolveInstantCapacity`+`CIRCUIT_BREAK_RATIO=0.9`），分子=当日各物化行 checkedInCount 之和。**改点优先级**：① 真正执行红线4 的核销写路径 `checkin/service/checkin.ts:156`（现用单时段 capacity 当分母→达标暂停当日全部时段，口径错）；② 通用熔断 `booking/domain/rules.ts:45`；③ `slots/page.tsx:39` 仅展示判红、随之改。详见下方 F1。
  - **〔评审 F1🔴 漏改真正熔断点〕** 计划只点 `slots/page.tsx:39`（仅展示判红）。**真正执行红线4（达90%停当日预约）的代码在核销写路径 `checkin/service/checkin.ts:156`**：`circuitBroken = result.capacity>0 && checkedInCount/result.capacity >= CIRCUIT_BREAK_RATIO`，其中 `result.capacity` 是**当前单时段**容量（从该 slot 的 UPDATE RETURNING 取回），达标后却 `UPDATE booking_slot SET status='PAUSED' WHERE status='ACTIVE'`（暂停**当日全部** ACTIVE 时段）——**单时段口径触发园区级停约，语义错**。另 `booking/domain/rules.ts:45` 的通用熔断函数同样按传入 capacity 判定。**口径统一范围必须含 `checkin.ts:156` + `rules.ts:45`，不止 slots 展示页**，否则改了显示、红线4 实际触发仍用错分母。
  - **设计约束**：`checkin.ts` 现把熔断**内联**进核销写路径，是刻意为之——避免 `import` booking 模块（eslint-boundaries 禁模块互依，见该文件 165-169 注释）。改用瞬时承载分母时，instantCapacity 取值须在核销写路径内可得而不破边界（route 层注入 / 直读 SysConfig），别想当然直接 import booking。
- **B31 规则层（PRD 1.2 防黄牛红线）**：
  - **每日总库存总闸**：新表 `BookingDailyCounter(date PK, total_booked)` + SysConfig `booking.daily_total_stock`；下单事务内 `UPDATE … SET total_booked+1 WHERE date=$d AND total_booked < $limit`（原子守卫，affected=0=满）。取消/爽约回退 `GREATEST(0,total_booked-1)`。
  - **单证/手机单日上限 N**：SysConfig `booking.daily_limit_per_idcard`/`per_phone`（默认 1）。**N=1 走现有部分唯一索引快路径；N>1 走 `pg_advisory_xact_lock(hashtext(idcard+date))` + count 校验**。手机上限默认可宽/可关（家庭多证同手机场景，待 PRD 确认）。
  - 阈值经 **app 路由层从 configService 读出注入 booking service**（守边界，沿用 `slot-roll.ts:24` 注入范式）。
